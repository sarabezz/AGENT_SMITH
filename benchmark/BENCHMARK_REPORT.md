# Agent Smith — Benchmark Report

This report compares several LLMs driving the same agent on the same tasks.
The raw numbers (one row per run, with per-step metrics) are generated by `make_report.py`
in [`benchmark/RESULTS.md`](benchmark/RESULTS.md). This file explains how they were obtained
and what they mean.

---

## 1. Setup

### 1.1 Tasks

**SWE-bench (main benchmark): 3 real GitHub issues**

| Task | Repository | What the bug is about |
|---|---|---|
| `sympy__sympy-23534` | sympy | `symbols(..., cls=Function)` creates Symbols instead of Functions when the names have an extra layer of parentheses |
| `sympy__sympy-14711` | sympy | adding a vector and `0` fails (`Vector + 0` raises an error) |
| `pydata__xarray-4629` | xarray | merging datasets with `combine_attrs="override"` keeps a *reference* to the first object's attributes instead of a copy |

Each task comes with:

- the **issue text** written by a real user (the only description the agent receives),
- a **Docker image** with the repository at the commit where the bug exists (`/testbed`),
- a **hidden test** (`eval_script`) used only for grading. It is never shown to the model.

**MBPP (used for the ablation): 5 short Python problems** (tasks 2–6 of the exam set).

### 1.2 Models

All models are **free tiers**, called through OpenAI-compatible APIs.

| Model | Provider | Size | Reasoning |
|---|---|---|---|
| `nvidia/nemotron-3-super-120b-a12b:free` | OpenRouter | 120B (12B active) | disabled |
| `cohere/north-mini-code:free` | OpenRouter | — | disabled |
| `qwen/qwen3.8-27b` | Groq | 27B | `reasoning_effort: none` |
| `dots-studio/dots-3-note-preview:free` | OpenRouter | — | disabled |
| `nvidia/nemotron-3.5-lightning:free` | OpenRouter | — | disabled |
| *`nvidia/nemotron-3-ultra-550b-a55b:free`* | *OpenRouter* | *550B (55B active)* | *disabled* |

Reasoning was disabled on every model so that all of them are compared under the same
conditions and the output token budget is spent on the answer.

**Model changes during the benchmark:**

- `google/gemma-4-31b-it:free` and `poolside/laguna-s-2.1:free` were in the first list, but were
  "temporarily rate-limited upstream" for 3 days in a row. They were replaced.
- `nemotron-3-ultra` timed out on two different days, so only 1 of its 3 runs finished. It is
  kept as an extra data point, and `nemotron-3.5-lightning` was added to complete the 5 × 3 grid.

### 1.3 The agent

The same agent, prompt and tools for every model. Only the model changes.

- **Loop:** Thought → one Python code block → the code runs in the sandbox → Observation → next step,
  until the model calls `final_answer(...)`.
- **Tools (MCP server `mcp_tools_swebench.py`):** `search_code`, `list_files`, `read_file`,
  `edit_file`, `run_command`, `run_tests`, `get_patch`. Every command runs **inside the task's
  Docker container**.
- **Prompt method:** reproduce the bug → find the code → fix it → reproduce again + run the
  module's tests → submit the `git diff`.
- **Solution submitted:** the **real** `git diff` of the container (`get_patch`), not the text the
  model typed. If the model never called `final_answer` but did change the code, the diff is
  still submitted ("auto-submit") and the run is marked as *not submitted* by the model.

### 1.4 Limits (per task)

| Limit | SWE-bench | MBPP |
|---|---|---|
| Max iterations | 30 | 10 |
| Max input tokens (total) | 300,000 | 6,000 |
| Max output tokens (total) | 10,000 | 1,500 |
| Max output tokens per call | 1,000 | 400 |
| Max time | 900 s | 120 s |
| Tool outputs | shortened to 6,000 characters; older observations compacted (last 2 kept in full) | 2,000 characters |

### 1.5 How the runs were made

- `run_benchmark.py` runs every model on every task, each run in its **own process**, with
  `--no-fallback` (the run uses only that model, never a backup one).
- Runs that failed because the **LLM was unavailable** (rate limit, timeout, missing key) are
  marked *unfinished* and retried another day. Runs where the agent **tried and failed** count
  as real results.
- Because of the free-tier quotas (OpenRouter: 50 requests per day), the runs were spread over
  **October 7–20, 2026**.
- **Correctness** is checked with the official grader (`moulinette_eval validate`): the patch is
  applied to a **fresh container** and the hidden test must pass. `make_report.py` caches each
  verdict next to the run.

## 3. Ablation: does the `run_tests` tool help?

**Question:** does giving the agent a tool that runs the task's real tests make it better?

**One change only.** Same model (qwen3.8-27b), same 5 MBPP tasks, same prompt and limits.
The only difference:

| | With tools | Without tools (`--no-tools`) |
|---|---|---|
| MCP server | started | not started |
| How the agent checks its code | calls `run_tests(...)`: the task's own tests run in a separate sandbox | writes its **own** `assert` lines and reads the result |

**Results** (from section 2.2):

| | With tools | Without tools | Change |
|---|---|---|---|
| Correct | 5/5 | 5/5 | same |
| Avg iterations | **1.2** | 2.4 | **half** |
| Avg input tokens | **737** | 1,475 | **half** |
| Avg output tokens | **112** | 236 | **half** |

**Why half?** With the tool, the agent can test **and** submit in the same code block:
if the tests pass, `final_answer` runs in that same step, so most tasks finish in **1 step**.
Without the tool, it needs one step to write the code and its own checks, then a second step
to read the result and submit. And since the whole history is sent again at every step,
twice the steps means about twice the tokens.

**What it shows:** on these tasks, the tool did not change *accuracy* (both reach 5/5),
but it made the agent **twice as efficient** (fewer steps, fewer tokens).

**Notes:**

- The average *time* (1.2 s vs 9.4 s) is not a fair comparison: two of the no-tools runs
  (tasks 4 and 6) took about 21 s each, most likely because of waits for Groq's per-minute
  limit, not because of the tool.
- 5 easy tasks and 1 model are a small sample. Both variants solved everything, so this
  ablation cannot show whether the tool improves accuracy on *harder* tasks.
